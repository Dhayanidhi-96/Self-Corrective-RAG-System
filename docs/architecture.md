# Architecture Blueprint - Self-Corrective RAG System

This document describes the technical architecture, component design, state representations, and orchestration logic for the Self-Corrective RAG System.

---

## 1. System Components

The system is organized into decoupled modules to ensure maintainability, testing, and clean separation of concerns.

```
   ┌─────────────────────────────────────────────────────────────┐
   │                       LangGraph Orchestrator                 │
   │                                                             │
   │  ┌──────────┐    ┌─────────────────┐    ┌────────────────┐  │
   │  │ Retrieve │ ──>│ Grade Documents │ ──>│ Route Decision │  │
   │  └──────────┘    └─────────────────┘    └───────┬────────┘  │
   │       ▲                                         │           │
   │       │ (web chunks)                            │ (fallback)│
   │       │                                         ▼           │
   │  ┌──────────┐                         ┌──────────────────┐  │
   │  │ Generate │ <────────────────────── │ DuckDuckGoSearch │  │
   │  └────┬─────┘                         └──────────────────┘  │
   │       │                                                     │
   │       ▼                                                     │
   │  ┌──────────┐                                               │
   │  │ Critique │ ── (Pass) ──> [Deliver Answer]                │
   │  └──────────┘                                               │
   └─────────────────────────────────────────────────────────────┘
```

### Component Breakdown
1.  **Ingestion & Vector Storage (`app/retrieval/`)**:
    *   **Text Splitter**: Splits documents using token or character count guidelines (e.g., `RecursiveCharacterTextSplitter` with `chunk_size=1000`, `chunk_overlap=200`).
    *   **Embedding Generator**: Uses Google AI Studio's `text-embedding-004` to create dense vectors.
    *   **ChromaDB Manager**: Connects to a local Chroma database, manages collections, inserts chunks with metadata, and queries them.
2.  **Generative Engine (`app/generation/`)**:
    *   Synthesizes answers from context documents using Google's `gemini-1.5-flash`.
    *   Handles template filling (injecting context + question) and returns raw or structured outputs.
3.  **Critique & Grading Agents (`app/critique/`)**:
    *   **Document Grader**: Evaluates retrieved chunks against the user's question, returning a binary relevance score (`yes` or `no`).
    *   **Hallucination Grader**: Evaluates generated text against retrieved chunks, returning a binary score (`yes` or `no`).
    *   **Answer Grader**: Evaluates generated text against the original question, returning a binary utility score (`yes` or `no`).
4.  **Fallback Web Searcher (`app/utils/`)**:
    *   Performs free web searches using `duckduckgo-search`.
    *   Aggregates the top 3 snippet results and wraps them into Document objects for synthesis.
5.  **Stateful Orchestrator (`app/workflows/`)**:
    *   Defines the `GraphState` data model.
    *   Coordinates the execution graph using **LangGraph**.
    *   Maps transitions between nodes using conditional routing edges.

## 2. Graph State & Data Models

In LangGraph, state is passed from node to node using a structured dictionary/class. We will define the state using Python's `TypedDict`.

```python
from typing import List, TypedDict
from langchain_core.documents import Document

class GraphState(TypedDict):
    """
    Represents the state of our cyclical workflow.
    """
    question: str                # The user's original query
    generation: str              # The synthesized answer generated by LLM
    documents: List[Document]    # List of retrieved/active document chunks
    search_query: str            # Optimized search query if fallback is triggered
    hallucination_retry: int     # Count of hallucination retry attempts (capped to avoid infinite loops)
    web_search_triggered: bool   # Track if web search fallback was used
```

## 3. Grader Agents & Prompt Logic

To make the critique system reliable, we will use **Structured LLM outputs** (via Pydantic) to force the Gemini model to return clean, binary JSON grades instead of verbose explanations.

### A. Document Grader Pydantic Schema
```python
from pydantic import BaseModel, Field

class GradeDocument(BaseModel):
    """Binary score for document relevance check."""
    binary_score: str = Field(
        description="Relevance score: 'yes' if document is relevant to the question, else 'no'"
    )
```

### B. Hallucination Grader Pydantic Schema
```python
class GradeHallucination(BaseModel):
    """Binary score for hallucination check."""
    binary_score: str = Field(
        description="Hallucination score: 'yes' if the generation is strictly grounded in the documents, else 'no'"
    )
```

### C. Answer Grader Pydantic Schema
```python
class GradeAnswer(BaseModel):
    """Binary score for checking if the answer actually addresses the user's question."""
    binary_score: str = Field(
        description="Utility score: 'yes' if the answer directly addresses and resolves the user's question, else 'no'"
    )
```

## 4. LangGraph Nodes & Flow Routing

The execution graph is composed of **Nodes** (actions) and **Edges** (conditional routing decisions).

### Nodes
*   `retrieve`: Queries ChromaDB for documents based on `question` and saves them in the `documents` list.
*   `grade_documents`: Iterates through `documents`. For each document, asks the *Document Grader* if it's relevant. Keeps relevant documents. If ANY document is found irrelevant, or the document list is empty, it sets a internal state flag indicating that Web Search fallback is required.
*   `web_search`: Uses a query reformulator to turn `question` into a search-engine friendly string, queries DuckDuckGo, converts results to `Document` chunks, and appends them to the active `documents` state.
*   `generate`: Takes current `documents` and `question`, prompts `gemini-1.5-flash`, and writes the answer to `generation`.
*   `fallback_refusal`: If retrieval and search both fail to yield relevant facts, writes a polite, graceful refusal to `generation` to prevent hallucination.

### Conditional Edges
*   `decide_to_generate`: Evaluates the state after document grading.
    *   If all documents are relevant $\rightarrow$ route directly to `generate`.
    *   If some/all documents are irrelevant $\rightarrow$ route to `web_search` to fetch supplementary data.
*   `grade_generation`: Evaluates the generation.
    *   *Step 1: Hallucination Check*. If hallucination detected $\rightarrow$ if `hallucination_retry < 3`, increment retry count and route back to `generate` for a fresh attempt with strict framing. Otherwise, route to `fallback_refusal`.
    *   *Step 2: Answer Utility Check*. If not hallucinating but fails to answer the question $\rightarrow$ route to `fallback_refusal` or `web_search`. If it passes both $\rightarrow$ route to `__end__` to return the answer to the user.
